# 파이프라인 카드 「현재 상태」 코멘트 — 설계서

- 작성일 2026-09-04 · 브랜치 `feat/pipeline-comment` (base `14a02d7`)
- 실측 기준일 **2026-09-04**. 숫자는 매일 변한다 — 인용 전에 그날 다시 셀 것.

## 1. 문제

파이프라인 보드의 카드는 **단계(`stage`)와 기관밖에 말해 주지 않는다.** 그래서
"압류가 들어와 삭제도 못 하고 상담예정으로도 못 넣는" 애매한 건이 어느 칸에 있든
**왜 거기 멈춰 있는지가 카드에 안 적힌다.** 담당자는 카드를 눌러 기업상세를 열어야만 알 수 있다.

실제 사례 — `달성종합중기(지원중기)` (실측):

| | |
|---|---|
| 살아있는 카드 | **2장** — 신용보증재단 `부결/반려` · 소상공인시장진흥공단 `기관신청대기/방문예정` (둘 다 `manual`) |
| 최신 소통내역 | `chat_memo` / 관호 / 2026-08-13 / `@달성종합중기(지원중기) 2026.8 거주지 가압류` |
| `note_company_links` | **0건** |

→ **답이 이미 DB 에 있는데 보드에서 안 보인다.** 이 설계는 그걸 카드로 끌어올린다.

⚠️ 같은 이름의 **휴지통 기업이 2개 더 있다**(`feb57748…` · `2700cba1…`).
조인키는 **`company_id` 뿐**이다 — 이름으로 잇는 경로를 새로 만들지 말 것(CLAUDE.md 2절).

## 3. 결정 사항 (사용자 승인 2026-09-04)

| # | 결정 | 근거 |
|---|---|---|
| D1 | **저장 단위 = 기업** | "압류가 들어왔다"는 기관과 무관한 기업 사실. 카드 2장 이상인 기업이 242개라 카드 단위면 같은 문구를 2~6번 써야 하고, 하나만 쓰면 나머지 카드는 자동표시라 화면이 어긋나 보인다 |

## 4. 설계

### 4-1. 저장 — `companies` 컬럼 3개 추가 (**새 테이블 0개 · RLS 신규 작업 0건**)

```sql
alter table public.companies
  add column if not exists status_comment    text,
  add column if not exists status_comment_at timestamptz,
  add column if not exists status_comment_by text;
```

- **`status_comment` 가 비어 있으면(`null` 또는 공백) 자동표시**, 값이 있으면 그 문구. 이 한 줄이 요구사항 2·3·4를 전부 표현한다.
- `_at`/`_by` 를 같이 두는 이유: 자동표시 줄은 `관호 · 8/13` 을 달고 나오는데 **수동 문구만 출처가 없으면 덜 믿을 만해 보인다.** "이 문구 언제 적은 거지"가 이 기능의 핵심 질문이다. 기존 `other_reason_note`/`other_reason_at`, `closed_by`/`closed_at` 과 같은 계열.
- **새 테이블을 만들지 않는 이유**: `companies` 는 RLS 정책·트리거가 이미 붙어 있어 컬럼 추가만으로 정책이 그대로 적용된다. 새 테이블이면 CLAUDE.md 2-2 체크리스트(RLS 켜기 · anon 회수 · `truncate/references/trigger` 회수 · 옛 정책 확인)가 전부 붙는데 얻는 게 없다.
- **타입은 `text`.** 숫자 컬럼이 아니라 2026-08-15 `companies.fee` integer 사고 계열과 무관하지만, 길이 제한을 두지 않는다는 뜻으로 명시한다.
- `companies` 로드는 `select("*")`(App.js:6947 · 4826) 이라 **새 컬럼이 자동으로 실려 온다** — 로드 코드 수정 0줄.
- 파일: `파이프라인_현재상태_코멘트_컬럼추가.sql` / `_rollback.sql` / `_검증.sql`

### 4-2. 자동표시 — 읽기 (새 테이블 0개 · 카드 데이터 안 건드림)

`PipelineView` 진입 `useEffect` 에서 **조회 2개**, 둘 다 `fetchAllRows`:

| 조회 | `cols` | `build` |
|---|---|---|
| `activity_logs` | `id, company_id, log_type, memo, logged_by, assignee, created_at` | `deleted_at is null` **＋ `log_type in (manual_memo, quick_memo, chat_memo)`** |
| `note_company_links` | `id, company_id, source, item_text, at, author` | `deleted_at is null` |

⚠️ **`orderBy`/`tieBreak` 는 기본값(`created_at` → `id` 오름차순)을 그대로 쓴다**(CLAUDE.md 2-5).
최신 1건은 **JS 에서 최댓값으로 고른다** — 페이지 경계가 흔들리지 않게 하기 위함.

이걸 `Map<company_id, { comm, note }>` 로 접는다 — **기업당 최신 1건씩**:

- **💬 소통내역 줄** ← `activity_logs` 3종 중 `created_at` 최대
- **📝 업무노트 줄** ← `note_company_links` 중 `at` 최대

**순수 계산 함수 `buildStatusAutoMap(logs, links)`** 하나로 뽑는다 — supabase 를 안 건드려야
테스트에서 실제 DB 덤프를 그대로 먹일 수 있다(`test-nocard.mjs`·`test-note-links.mjs` 와 같은 방식).

**텍스트 손질 2가지 — 둘 다 실측 근거**

1. **선두 `@업체명` 제거.** `chat_memo` 는 `@달성종합중기(지원중기) 2026.8 거주지 가압류` 처럼
   태그가 앞에 붙는다 → 표시할 땐 `2026.8 거주지 가압류`.
   ⚠️ **`taggedCompanyRefs`/`findTaggedCompanies` 를 쓰지 않는다.** 저건 본문 전체에서 태그를 찾는
   매처라 목적이 다르고, 후자는 접두 과매칭이 있는 채팅 전용이다(CLAUDE.md 🕒 절).
   여기 필요한 건 **"이 줄이 이 회사 이름으로 시작하면 그만큼 잘라낸다"** 뿐이다 → `stripLeadingTag(text, coName)`.
2. **줄바꿈 접기 + 말줄임은 기존 공용 `memoPreview(v, max)`(App.js:14433) 재사용.** 새로 만들지 않는다.

### 4-3. 수동 입력 — 쓰기 (**새 저장 경로 0개**)

- 카드의 `✎` → **기존 공용 `MemoEditModal`(App.js:14388)** 그대로.
  `Ctrl+Enter` 저장 / `Esc` 취소(window capture) / 🏢 업체명 표시 / 이탈 확인이 이미 들어 있다.
  CLAUDE.md 「메모 확대 편집 팝업」 절: **"새 메모 칸을 만들면 이걸 쓸 것."**
  ⚠️ 이 컴포넌트에 supabase 를 들이지 않는다 — 값만 돌려주고 저장은 호출부가 한다.
- 저장은 App 의 **기존 `onPatchCompany(id, patch)` 패턴(App.js:9132)** 을 `PipelineView` 에도 넘겨
  `companies` UPDATE + 상태 반영. `companyById`(App.js:7825) → `pipelineCardData`(7833) 가
  **자동으로 재계산돼 같은 기업 카드 2~6장이 한꺼번에 바뀐다** — D1 이 공짜로 성립한다.
- **빈칸으로 저장 → 세 컬럼 모두 `null`** → 자동표시 복귀(요구사항 4번).
- `writeGuarded` 재시도 큐 **사용 가능**하다 — 저장 뒤에 딸린 연동이 없다(CLAUDE.md 2-7 해당 없음).

## 5. 범위 밖 (일부러 안 하는 것)

- **모바일** — `PipelineView` 렌더 지점은 `CRMApp` 한 곳뿐이다(`TeamNotesSection` 과 다른 점). 영향 0.

- **코멘트 이력 / 여러 건** — 1건 덮어쓰기. 이력이 필요하면 소통내역에 쓰면 된다.
- **Realtime 구독** — 지금 보드에도 없다.
- **`note_auto` 포함** — D2 에서 제외.
- **기존 로직 수정** — `pipelineCardData`·`moveCards`·`syncPipelineFromCase`·`resyncAutoCards`·
  카드 이동/삭제/종결/기타사유는 **한 줄도 안 건드린다.**

## 7. 알려진 한계 (구현 후에도 남는 것)

1. **카드 51%에 자동표시가 없다.** 데이터가 없어서다.
2. **수동 문구는 기업 단위**라 "재단 건만 애매하다"는 기관별 구분을 못 한다(D1).
3. `activity_logs` 의 `issue_update`·`status_change`·`action_update` 는 **`company_id` 가 비어 있어**
   (전 행 0건) 애초에 기업으로 이을 수 없다. 이 설계는 그 셋을 안 쓴다.
4. `note_company_links` 는 같은 문장이 이월·가져가기로 여러 번 들어온다(CLAUDE.md 🕒 절).
   **최신 1건만 쓰므로 표시에는 영향이 없다** — 기업상세 타임라인처럼 접을 필요가 없다.
