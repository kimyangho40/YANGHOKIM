# 📢 공고 매칭 시스템 — 설계

작성 2026-08-30 · 상태: 승인됨(구현 대기) · 새 테이블 1개 / 새 API 1개

지원사업 공고문을 첨부하면 자격 조건을 읽어, 우리 업체 중 해당되는 곳을 찾아 주는 기능.

---

## 1. 왜 필요한가

지금은 담당자가 공고문을 눈으로 읽고, 기업목록을 훑으며 머릿속으로 대조한다.
살아있는 기업이 **404개**라 한 공고를 제대로 훑는 데만 한나절이 걸리고,
지역·업력·매출처럼 기계가 정확히 잴 수 있는 조건에서 사람이 빠뜨린다.

→ 기계가 잴 수 있는 것은 기계가 재고, 사람은 **애매한 것과 최종 판단**만 본다.

---

## 2. 이번 범위 (1차)

**한다**

- 공고 첨부(PDF · 이미지 · 텍스트 붙여넣기) → AI가 자격 조건 추출
- 조건을 사람이 화면에서 수정
- `companies` 대조 → **유력 / 애매 / 제외** 3단계 판정 + 조건별 근거
- 조건 수정 후 **재매칭**(코드만 — AI 호출 0 · 비용 0 · 즉시)
- 결과 체크 선택 → 담당자 **업무노트** 또는 팀 **일정**으로 보내기
- 공고 저장 + **신청기간 마감 D-7/D-3/D-1 배너**

**안 한다 (2차 이후)**

| 미룬 것 | 이유 |
|---|---|
| 드라이브 서류 검증 | 폴더 연결 **105/404** · OAuth 앱이 **테스트 모드**(코드로 못 고침) — 8절 |
| 「확실」 판정 등급 | *서류로 확인됨* 이어야 의미가 있다. 서류 없이 "확실"은 거짓말이다 |
| 애매 건 AI 재판정 | 1차는 코드 매칭만으로 시작(2026-08-30 사용자 결정) |
| 기관 디렉토리(256곳) | 완전 별도 기능. 데이터가 아직 없다(2026-08-30 사용자 결정) |
| 기업마당 자동 수집 | 인증키 발급이 선행 — 9절에 조사 결과 |
| 공고 원본 파일 보관 | Storage 버킷은 RLS를 새로 짜야 한다(CLAUDE.md 2-2). `external_url` + 조건별 원문 인용으로 대신한다 |

## 4. 이미 있어서 새로 만들지 않는 것

**이 목록의 함수를 고치지 말 것.** 호출만 한다. 전부 다른 화면이 같이 쓰는 공용 함수다.

|---|---|---|
| `BIZ_SCALE_TABLE` · `bizScaleCap` · `bizAvgRevenue` · `judgeSmallBiz` | App.js | 규모(소상공인/소기업/중소기업) 판정 · 업종 키워드 표의 뿌리 |

| `team_notes.checklist` 의 `is_sched` 항목 + 기존 저장 경로 | App.js | 팀 일정으로 보내기 |
| `api/parse-credit.js` 구조 | api/ | 새 엔드포인트의 뼈대(파일 하나로 완결 · `denyUnauthorized` 첫 줄 · raw fetch) |
| `callApi()` | App.js | 프런트에서 `/api/*` 호출 |
| `fetchAllRows(table, cols, opts)` | App.js | 공고 전건 조회 |
| `writeGuarded` | App.js | 저장 |

기존 키워드의 `amount`를 바꾸면 회귀다.

## 5. 데이터 모델 — 새 테이블 **`announcements` 1개뿐**

```sql
create table public.announcements (
  id            uuid primary key default gen_random_uuid(),

  -- 출처 (★ 자동수집 확장의 이음매)
  source        text not null default 'manual',  -- 'manual' | 'bizinfo' | …
  external_id   text,          -- 원본 시스템의 고유 id (기업마당 공고 id 등)
  external_url  text,

  -- 내용
  title           text not null,
  agency          text,        -- 소관기관 (자유 텍스트)
  support_summary text,
  apply_start     date,
  apply_end       date,

  -- 조건
  conditions       jsonb,      -- ★ 확정본. 매칭이 보는 유일한 값
  conditions_ai    jsonb,      -- AI 추출 원본 (읽기 전용 보존)
  conditions_state text not null default 'pending',  -- pending | extracted | confirmed

  -- 매칭 결과 (★ 반드시 둘로 나눈다 — 아래 경고 참고)
  match_summary jsonb,         -- { ranAt, ranBy, engine, counts:{유력,애매,제외} }
  match_rows    jsonb,         -- 업체별 상세

  -- 관리
  status     text not null default 'active',   -- active | closed
  created_by text,
  created_at timestamptz not null default now(),
  updated_at timestamptz,
  deleted_at timestamptz
);

create unique index announcements_source_external_uniq
  on public.announcements (source, external_id)
  where external_id is not null;
```

### ⚠️ `match_summary` / `match_rows` 를 나누는 것이 이 표에서 제일 중요한 결정이다

목록 화면은 **`match_summary` 만 `select`** 한다. 자동 수집이 켜져 공고가 수백 건이 되는
순간, 둘을 같이 부르면 목록 한 번에 수 MB가 오간다. 지금 나눠 두면 나중에 안 터진다.
`match_rows` 는 **상세를 열 때 그 행만** 다시 읽는다.

### ⚠️ unique 인덱스는 **삭제분을 포함**한다 (`where deleted_at is null` 을 넣지 않는다)

파이프라인 카드 휴지통과 **같은 규칙**이다. 사람이 "관심 없음"으로 지운 공고가
다음 자동 수집 때 되살아나면 안 된다. 수집기는 삭제분까지 조회해 "이미 받은 공고"로 건너뛴다.

### 지금 일부러 안 넣은 컬럼

- `source_agency_id` — 기관 디렉토리가 이번 범위에서 빠졌다. 그 기능을 할 때
  `add column if not exists source_agency_id uuid` 한 줄로 붙는다. 지금 넣으면
  가리킬 테이블이 없는 죽은 컬럼이 된다.
- `auto_extract` 설정 — 자동 수집(2차)과 한 쌍이다. 그때 같이 넣는다.

### RLS — 만드는 커밋에서 같이 (CLAUDE.md 2-2 체크리스트 전부)

- [ ] `alter table public.announcements enable row level security;`
- [ ] 정책 4종(select/insert/update/delete) 전부 `to authenticated` + `is_approved()`.
      **`to public` / `to anon` 정책은 만들지 않는다.**
- [ ] `revoke all on public.announcements from anon;`
- [ ] `revoke truncate, references, trigger on public.announcements from authenticated, anon;`
- [ ] 실행 후 **별도 조회**로 재확인 (2-2: `revoke`는 grantor가 다르면 조용히 아무것도 안 한다)
- [ ] 배포 전 점검 — RLS 꺼진 public 테이블 조회가 0행인지

파일: `공고매칭_announcements_테이블추가.sql` / `_rollback.sql` / `_검증.sql`

## 6. 조건 추출 — `api/parse-announcement.js`

`parse-credit.js` 의 형제. **파일 하나로 완결**(서버리스 함수는 `_` 시작 공유 모듈을 못 쓴다),
첫 줄 `denyUnauthorized(req, res)`, raw fetch, `claude-opus-5`.

### 추출 스키마 (`conditions`)

```js
{
  version: 1,
  regions:    { include: [{ sido:"서울", sigungu:"강남" }], note:"" },   // [] = 전국
  industries: { include: ["제조","도소매"], exclude: ["유흥","사행성"], ksic:["C"] },
  scale:      "소상공인" | "소기업" | "중소기업" | null,
  revenue:    { min:null, max:12000000000, basis:"연매출" | "3년평균" },
  age:        { min_months:12, max_months:null, basis:"설립일" },
  employees:  { min:null, max:50 },
  excludes_text: ["국세·지방세 체납", "휴·폐업"],   // 코드로 못 재는 조건 원문
  quotes:     { regions:"…공고 원문…", scale:"…", revenue:"…", … }
}
```

### ⚠️ 추측 금지 — 이 저장소의 파서들이 지켜 온 원칙 그대로

- **`null` = "공고에 안 적혀 있음" = 그 조건은 안 본다.**
  절대 "전국"이나 `0`으로 채우지 않는다. 채우는 순간 없던 조건이 생겨 판정이 통째로 틀린다.
  (옛 사고 계열: `"1억"` → 1원, 커밋 `d3df072`)
- **`quotes` 가 없으면 이 기능은 못 쓴다.** 사람이 조건을 고칠 때도, 결과의 근거를 볼 때도
  공고 원문이 필요하다. 스키마에서 `required` 로 둔다.
- 모델이 형식을 못 맞추면 **빈 값으로 두고 화면에 ⚠️ 를 띄운다.** 값을 지어내지 않는다.

### 입력 3종

| 입력 | 처리 | 비용 |
|---|---|---|
| PDF | `document` 블록(base64) — parse-credit 과 같은 방식 | 크다 |
| 이미지 | `image` 블록 | 중간 |
| 텍스트 붙여넣기 | 그대로 | 작다 (약 1/10) |

## 7. 매칭 엔진 — 코드가 돌린다

**클라이언트(App.js)에서 계산한다. `companies` 는 이미 메모리에 있다 → supabase 조회 0건 추가.**
저장은 결과 1행 UPDATE 뿐. 그래서 재매칭이 즉시이고 공짜다.

상수 `MATCH_ENGINE_VERSION = 1` 을 `match_summary.engine` 에 같이 적는다 —
엔진이 바뀌면 옛 결과와 새 결과를 구분할 수 있어야 한다.

### 7-1. 지역 — 함수 하나 `normRegion(text)` 를 **세 출처가 같이 통과**

| 출처 | 원문 | `normRegion` 결과 |
|---|---|---|
| CRM | `서울_강남` / `경기 시흥` / `경기` | `{서울,강남}` / `{경기,시흥}` / `{경기,""}` |
| 공고 | `서울특별시 강남구` | `{서울,강남}` |
| 서류(2차) | `서울특별시 강남구 테헤란로 123` | `{서울,강남}` |

규칙:
1. 시도 별칭표 17개 — `서울|서울시|서울특별시` → `서울`, `경기|경기도` → `경기`, `충남|충청남도` → `충남` …
2. `_` · 공백 · `/` · `,` 로 분리
3. 시군구는 접미사 `시`/`군`/`구` 제거. **단 떼고도 글자가 남을 때만** (`중구` → `중` 은 유지)
4. **비교는 정규화 결과끼리만 한다.** 한쪽만 정규화하면 어긋난다.

⚠️ **반드시 시도와 쌍으로 비교한다.** `경기 광주`(경기도 광주시) 와 `광주광역시` 는
시군구만 보면 같아진다. 시도가 다르면 시군구가 같아도 불일치다.

⚠️ **공고가 우리보다 깊은 단위를 요구하면 `unknown`.**
우리는 `경기_고양` 인데 공고가 `고양시 덕양구` 한정이면 일산 업체가 섞인다
→ "해당"이 아니라 **"애매"** 로 둔다.

⚠️ 공고 `regions.include` 가 빈 배열이면 **전국** — 이 조건은 전원 `pass`.

### 7-2. 업종 — 제일 약한 고리라는 걸 인정하고 설계한다

- 우리 `industry` 를 콤마·슬래시로 쪼개 **토큰 여러 개**로 만든다(다중값 143건).
- 공고 `include` 하나라도 부분일치 → `pass`
- 공고 `exclude` 하나라도 부분일치 → **`fail`**
- 둘 다 안 걸림 → `unknown`
- 키워드 표는 `BIZ_SCALE_TABLE` 의 43업종 키워드를 **재사용·확장**한다.
  ⚠️ 새 표를 따로 만들면 둘이 어긋난다. 표는 하나다.

⚠️ **"제외 대상이 아님"을 확정하지 않는다.**
`industry` 가 `도소매업` 이라고 유흥업이 아니라고 단정할 근거는 없다.
그렇다고 전부 애매로 내리면 쓸모가 없어지므로 — **판정은 내리지 않고
근거란에 `⚠ 제외조건 미확인: 유흥업` 으로 표시만** 한다. 사람이 보고 거른다.

### 7-3. 규모 · 매출 · 업력 · 근로자수

| 조건 | 계산 | 함정 |
|---|---|---|
| 규모 | 기존 `judgeSmallBiz` / `bizScaleCap` **그대로 호출** | 소상공인은 근로자수까지 필요 → 대부분 `unknown` |
| 매출 | `basis` 에 따라 최근연도 또는 3년평균 (`bizAvgRevenue`) | `bigint` 확인됨 — 그대로 신뢰 |
| 업력 | `founded_year` + `founded_month` → 개월 | ⚠️ **월이 없으면 최대 11개월 오차** → 경계에 걸릴 때만 `unknown`, 안 걸리면 확정 |
| 근로자수 | `employee_count` | 142/404 — 없으면 `unknown` |

### 7-4. 종합 판정 — 규칙 한 줄

조건마다 `pass | unknown | fail` 을 매기고:

> **fail 이 하나라도 있으면 → 제외**
> **fail 없고 unknown 도 없으면 → 유력**
> **나머지 → 애매**

이 한 줄이 3단계를 자동으로 만들고, **왜 그렇게 됐는지가 조건별로 전부 남는다.**

### 7-5. `match_rows` 모양

```js
{
  company_id, name, assignee,
  verdict: "유력" | "애매" | "제외",
  checks: [
    { key:"region", state:"pass", label:"지역", got:"서울_강남", want:"서울 강남구" },
    { key:"employees", state:"unknown", label:"상시근로자", got:"", want:"5인 미만" },
    …
  ],
  notes: ["⚠ 제외조건 미확인: 유흥업"]
}
```

⚠️ **제외 행은 `checks` 에 떨어진 조건 1개만 담는다.** 전부 담으면 404개 × 8조건이 jsonb에 들어간다.
유력·애매 행은 전 조건을 담는다(근거를 다 보여줘야 하므로).

## 8. 화면 — 새 view `announce` (사이드바 더보기)

정산관리·배정DB와 같은 방식. **`CRMApp`(데스크톱)에서만 렌더한다 — 모바일 영향 0.**

## 9. 2차 — 드라이브 서류 검증 · 애매 건 AI 재판정

### 드라이브 검증의 선행조건 2개. 안 풀리면 시작해도 반쪽이다

1. 🔴 **OAuth 앱 테스트 모드 해제** — 직원 계정 403의 정체다(2026-08-30 확인).
   `drive.readonly` 는 구글의 **제한(restricted) 스코프**라 ① 테스트 사용자 100명 등록으로
   임시 우회하거나 ② 정식 게시하려면 **구글 앱 심사(+보안 평가)** 를 받아야 한다.
   **코드로 못 고치는 일이다.**
2. 🟡 **폴더 연결률 105/404** — 기존 「드라이브 연결」 일괄 자동연결을 다시 돌려 올린다.

### 읽기 전략 — 어느 시점에 어떤 서류만

| 단계 | 대상 | 읽는 것 | 왜 |
|---|---|---|---|
| ① | 후보(유력+애매) 전원 | 없음 — `scanCompanyDriveDocs` 로 **파일명만** | 이미 있는 분류기. Drive API 호출만 들고 AI 비용 0 |
| ② | 지역·업종이 `unknown` 인 업체 | **사업자등록증** 1종 | 주소·업태·종목이 한 장에 다 있다. 가성비 압도적 |
| ③ | 매출·규모가 `unknown` 인 업체 | 재무제표 → 부가세증명원 순 | 여기서부터 비싸다. 필요한 업체만 |
| ④ | `제외` 난 업체 | 안 읽는다 | 떨어진 걸 확인하려고 돈을 쓰지 않는다 |

### 서류가 없는 업체 · CRM과 다른 업체

- 없음 → `서류 미비 — CRM 데이터만으로 판정` 배지. **판정을 내리지도 올리지도 않는다.**
  서류가 없는 것은 정보이지 결격이 아니다.
- 다름 → `서류와 불일치` 배지 + 양쪽 값 나란히. **자동으로 CRM을 고치지 않는다.**
  `doc_scan` 이 `received_docs` 를 자동으로 안 덮는 것과 같은 이유 —
  "맞다고 착각하고 틀린 값으로 신청"이 미확인보다 훨씬 나쁘다.
- 2차가 들어오면 판정이 **유력 → 확실** 로 올라가는 등급이 하나 생긴다.

### 애매 건 AI 재판정 (2차)

- **한 공고당 호출 1회.** 애매 업체 전부를 묶어 보낸다. 업체별 호출은 100배 비싸다.
- ⚠️ **AI는 애매를 좁힐 뿐, 코드가 낸 `fail` 을 못 뒤집는다.**
  (파이프라인 번역표의 "매핑표보다 코드가 이긴다"와 같은 계열)
- 결과에 `🤖` 배지 — 사람이 코드 판정과 구분할 수 있게.

## 10. 기업마당 자동 수집 — 조사 결과 (2026-08-30 실측)

### 가능하다. 크롤링 불필요 — 공식 OpenAPI가 있다

```
GET https://www.bizinfo.go.kr/uss/rss/bizinfoApi.do?crtfcKey=…&dataType=json
  키 없음  → HTTP 200 {"reqErr":"인증키를 입력해주세요."}
  틀린 키  → HTTP 200 {"reqErr":"존재하지 않는 인증키 입니다."}
```

→ 엔드포인트가 **살아 있고, JSON을 주고, 서버에서 호출된다.** HTML 파싱이 필요 없다.
(추측한 RSS 경로 `…/AS/74/rss.do` 는 404 — **RSS가 있다고 쓰지 말 것.** 확인된 것은 이 API 하나다.)

### 인증키

**시스템URL 등록 방식으로 발급 가능**하다(2026-08-30 사용자 확인).
Vercel 배포 주소 `crm-beta-snowy.vercel.app` 로 등록한다.
IP 등록만 됐다면 Vercel 서버리스는 나가는 IP가 고정이 아니라 막혔을 것이다 — 이 갈림길은 통과했다.

⚠️ **키는 저장소·채팅에 절대 넣지 않는다.** Vercel 환경변수에만 둔다
(`ASSIGN_DB_SYNC_SECRET`·`SUPABASE_SERVICE_ROLE_KEY` 와 같은 자리).

### ⚠️ 아직 모르는 것 2개 — 키를 받아야만 확정된다. 추측으로 코드를 쓰지 않는다

1. **응답 필드명** — 명세 페이지(`apiDetail.do?id=bizinfoApi`)가 404라 실제 필드를 못 봤다.
   키를 받아 한 번 찍어 봐야 `external_id` · `apply_end` 매핑이 정해진다.
2. **공고 본문이 응답에 오는가** — 요약만 오면 **자격요건 상세는 본문 페이지를 한 번 더
   가져와야 한다**(그건 크롤링이다). 이게 2차 작업량을 크게 가른다.

### 주기 실행 — Apps Script 추천

| | Vercel Cron | **Apps Script 시간 트리거** |
|---|---|---|
| 설정 | `vercel.json` 신규 (현재 **없음**) | `apps-script/` 에 **이미 같은 패턴이 돌고 있다**(배정DB) |
| 빈도 | ⚠️ **Hobby는 하루 1회 + 시각도 부정확**(그 시간대 안 아무 때나). Pro면 분 단위 | 10분도 무료 |
| 인증 | Vercel이 자동 | 공유키 상수시간 비교 (`assign-db-sync.js` 와 같은 방식) |

→ **`api/bizinfo-sync.js` + Apps Script 시간 트리거.**
이 저장소에서 이미 검증된 구조라 새 인프라가 0이고 Vercel 플랜에 안 묶인다.

⚠️ **배정DB와 시크릿을 공유하지 말 것** — 별도 환경변수를 쓴다.
⚠️ 배정DB와 같은 안전장치를 답습한다: **0건 응답은 반영하지 않는다**
(원본 사고로 데이터가 날아가도 우리 쪽은 보존).

### 자동 수집 + 자동 매칭 — 비용 안전장치

"들어온 공고마다 자동 배지"는 **둘로 나눠야 안전하다**:

| | 비용 | 정책 |
|---|---|---|
| 조건 **추출** (AI) | 💰 유료 | ⚠️ **일일 상한**(예: 20건/일) + on/off 설정. 상한 없이 켜면 기업마당 신규 공고가 하루 수십 건이라 **월 수십만원**이 된다 |
| **매칭** (코드) | 0원 | 🟢 추출이 끝나면 **항상 자동**. 배지는 여기서 붙는다 |

상한을 넘긴 공고는 목록에 `미추출` 로 쌓이고 사람이 골라서 [추출] 을 누른다.

## 13. 회귀 위험 · 지켜야 할 규칙

- **공용 함수를 고치지 않는다** (4절 표). `bizScaleCap` 을 고치면 **기업목록 규모 배지**가 같이 바뀐다.
  키워드를 더하는 것은 안전, 기존 `amount` 를 바꾸는 것은 회귀.
- **새 테이블은 만든 커밋에서 RLS 전부** (5절 체크리스트).
- **`/api/parse-announcement.js` 첫 줄 `denyUnauthorized`**, 프런트는 `callApi()` 경유.
  검사가 없으면 누구나 호출해 `ANTHROPIC_API_KEY` 요금을 태울 수 있다.
- **전건 조회는 `fetchAllRows`** — 공고가 1,000건을 넘을 수 있다(2-5).
  `.limit(1000 초과)` 는 **에러도 경고도 없이 무시**된다.
- **목록은 `match_rows` 를 select 하지 않는다** (5절).
- **저장 경로를 새로 만들지 않는다** — 업무노트·일정 둘 다 기존 경로(8절).
- **모바일 영향 0** — `announce` 는 `CRMApp` 에서만 렌더.
