# 2026-07-28 · 업무노트 저장 실패 (조용한 실패)

담당자가 노트북에서 업무노트를 작성하고 저장을 눌렀는데 저장되지 않았다.
같은 시각 구글 드라이브 등 다른 서비스는 정상이었으므로 네트워크 전체 문제는 아니었다.
**화면에는 아무 오류도 뜨지 않았다.** 그게 이 사고의 본질이다.

## 무엇이 일어났나

- 7월 28일 `work_notes` 쓰기 기록: 관호·인선·유진·지혜·미현 5명은 정상(마지막 18:01 KST).
- **양호 계정만 7/28 쓰기 0건.** 마지막 쓰기는 7/27 22:20.
- → 전면 장애가 아니라 **특정 계정·기기의 세션 문제**로 좁혀졌다.

## 원인

### 1) 조용히 실패하게 만든 구조 (진짜 원인)

세션이 끊긴 상태에서 저장을 누르면 두 갈래로 갈리는데, **둘 다 화면에 표시가 없었다.**

**경로 A — 세션 갱신 실패 → 롤이 `anon`으로 강등**
`anon`에게 `work_notes` INSERT/UPDATE **GRANT는 남아 있고** RLS 정책만 `authenticated` 전용이다.
이 조합에서 UPDATE는 거부가 아니라 **0행 매칭**이 되고 PostgREST는 `204`를 준다.
→ `r.error`가 `null`이라 앱이 **성공으로 판단**하고 편집창을 닫았다. 저장된 것처럼 보였다.

**경로 B — JWT 만료 → 401**
`r.error`는 오지만 호출부가 이랬다.

```js
var r = await supabase.from("work_notes").update(upd).eq("id", editNote.id);
if (!r.error) { …화면 갱신·편집창 닫기… }   // else 가 없다
```

실패하면 **아무 일도 일어나지 않는다.** 버튼을 눌렀는데 반응이 없는 상태.

세션 복구 로직(`visibilitychange` 시 만료 60초 전이면 갱신)은 있었으나
**갱신 실패 시 `console.warn`만 하고 사용자에게 알리지 않았다.**

### 2) 범위 — 이 화면만의 문제가 아니었다

App.js의 쓰기 호출 208곳을 전수 분류한 결과:

| 분류 | 건수 |
|---|---|
| 오류를 확인조차 안 함 | 33 |
| 확인은 하나 사용자에게 안 알림 | 76 |
| 사용자에게 알림 | 99 |

**109곳(52%)이 실패해도 사용자가 몰랐다.** 알림이 있는 99곳도 경로 A(0행 204)는 못 잡았다.

### 3) 아니었던 것 (조사해서 배제)

- **RLS가 쓰기를 전면 차단한 것이 아니다.** `public` 실테이블 전부 `authenticated` 대상
  INSERT/UPDATE 정책 보유. `is_approved()`는 `profiles.status='approved'`를 보는데 **가입자 20명 전원 approved**.
  같은 날 다른 5명이 정상 저장한 것이 실측 반증이다.

## 조치 (2026-07-28)

**2단계 — 임시저장 (전 화면 공통)**
`useDraft()` 훅 하나로 통일. 입력 후 3초 뒤 브라우저에 보관하고,
**`visibilitychange`/`pagehide`에서는 즉시 보관**한다(iOS는 백그라운드 전환 시 탭이 정리돼 내용이 날아간다).
컴포넌트가 사라질 때도 보관한다. 다시 들어오면 `DraftNotice`가 "이어서 쓰시겠습니까?"를 띄운다.
적용: 업무노트 편집·새 노트 / 빠른 메모 / 빠른 업무 / 채팅(채널별) / 소통내역(업체별) / 모바일 새 노트.
**서버로는 보내지 않는다** — 실제 저장은 사용자가 누를 때만.

**3단계 — 저장 실패 처리**
`writeGuarded()`가 UPDATE/INSERT에 `.select()`를 붙여 **바뀐 행 수로 성공을 판정**한다.
0행이면 실패다(경로 A 차단). 실패는 사유를 **네트워크 / 로그인 / 권한 / 서버**로 구분해
화면 오른쪽 아래 띠에 크게 띄우고, 내용을 브라우저 큐에 보관한다.
연결 회복(`online` 이벤트)·화면 복귀·30초 주기·수동 버튼으로 자동 재시도하고, 성공하면 알린다.
재시도가 계속 실패하면 큐에 남고 다음 접속 때 다시 안내한다.

**4단계 — 이동 중 사용 대응**
오프라인이면 검은 띠로 "📴 오프라인입니다 · 연결되면 자동 저장됩니다" 표시.
저장 안 된 입력이나 실패 큐가 있으면 `beforeunload`로 이탈 경고.

**5단계 — 기록**
저장 실패·복구를 `activity_logs`에 `log_type='저장실패' / '저장복구'`로 남겨 나중에 집계 가능.
(네트워크 끊김이면 그때는 못 남기므로, 재시도가 성공한 시점에 '저장복구'로 함께 남긴다.)

## 사용자에게 반드시 안내해야 할 것

> **브라우저 임시 보관은 그 기기에만 남는다.**
> 노트북에서 쓰던 내용을 아이패드에서 복구할 수는 없다.
> 화면의 안내 문구에도 매번 같이 적어 두었다.

## 남은 위험 / 후속 제안

1. **`anon`에 남은 INSERT/UPDATE GRANT** — 회수하면 세션이 끊긴 상태의 쓰기가
   204(조용한 성공)가 아니라 401/403 명시적 에러가 된다. 근본 차단. **미조치(사용자 결정 대기).**
2. 아직 `writeGuarded`로 안 바꾼 쓰기 호출이 남아 있다(업무노트·모바일 노트 위주로 먼저 적용).
   기관현황·DB리스트 등은 대부분 alert이 있지만 **경로 A는 여전히 못 잡는다.**
3. 영구 로그인(localStorage 세션) 자체는 그대로다.
